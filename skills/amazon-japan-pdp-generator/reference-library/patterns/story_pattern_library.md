# Story Pattern Library

> A story pattern is a decision path, not a fixed page layout. Select one dominant pattern and at most two supporting patterns; never assemble one module per feature.

## Feature-led

- Pattern ID: `STORY-FEATURE-LED`
- Consumer trigger: The category is already understood and shoppers compare a familiar set of functions.
- Reference ASINs: B0GK1QFGF6, B0FWQY84L6
- Sequence: Value compression → Primary feature → Secondary feature cluster → Everyday fit → Comparison → Objection closure

USE:

- Bundle many functions into one hierarchy before assigning visuals
- Use chapters for coherent feature families
- Reserve comparison and support for the end

ADAPT:

- Limit feature clusters to one consumer question per visual
- Alternate at least one human scenario with technical chapters

AVOID:

- One feature equals one image
- Award or logo wallpaper
- A long unranked feature inventory

## Category Education

- Pattern ID: `STORY-CATEGORY-EDUCATION`
- Consumer trigger: The product category, workflow or reason to buy is unfamiliar.
- Reference ASINs: B0FQ5J7HFQ, B08131HFSG
- Sequence: Problem recognition → What the category does → Input or setup → Mechanism or transformation → Tangible outcome → Real scenario → Fit and conditions

USE:

- Explain the user task before technical vocabulary
- Turn abstract AI or wellness value into visible outputs
- Repeat the product after education so it remains a physical purchase

ADAPT:

- Use SwitchBot user language and approved product UI
- Keep education visual and short enough for Amazon scanning

AVOID:

- Leading with unexplained technology names
- Claiming category leadership without approved evidence
- Treating lifestyle scenes as technical proof

## Performance-led

- Pattern ID: `STORY-PERFORMANCE-LED`
- Consumer trigger: A measurable or observable result is the main reason to switch or pay more.
- Reference ASINs: B0F66LKTV6, B0FX81HWQ3, B0GK1QFGF6
- Sequence: Performance conclusion → Mechanism → Failure-point proof → Result in a real environment → Method or model comparison → Ownership confidence

USE:

- Put comparison conditions beside performance claims
- Connect numbers to visible user outcomes
- Break one major USP into specific failure-point proofs

ADAPT:

- Reduce every proof to one result, one mechanism and one source
- Use clean SwitchBot technical diagrams rather than dense ecommerce collages

AVOID:

- Decorative statistics
- Unqualified multipliers
- Tiny multi-column charts in Gallery

## Scenario-led

- Pattern ID: `STORY-SCENARIO-LED`
- Consumer trigger: Fit, routine or emotional context matters more than raw specifications.
- Reference ASINs: B0FQ5J7HFQ, B08131HFSG, B0FX81HWQ3
- Sequence: Audience moment → Pain in context → Product intervention → Before-after benefit → Second high-value scenario → Fit check → Confidence closure

USE:

- Choose scenes that answer a purchase question
- Keep the official product layer visually accurate
- Use scenarios to validate fit after the core value is understood

ADAPT:

- Use believable Japanese homes and work contexts
- Separate AI or stock scene layers from the official product layer

AVOID:

- Generic decorative lifestyle photography
- Making scenes carry unsupported claims
- Hiding the product to achieve mood

## Technology-led

- Pattern ID: `STORY-TECHNOLOGY-LED`
- Consumer trigger: The purchase depends on understanding an invisible mechanism, platform or system relationship.
- Reference ASINs: B0GK1QFGF6, B0F66LKTV6, B0FWQY84L6
- Sequence: Human value → Technology concept → Mechanism → Proof condition → Real-world effect → Compatibility or ecosystem → FAQ

USE:

- Start with the user benefit before naming the technology
- Use programmatic diagrams and source-linked labels
- Show one lived consequence after each technical chapter

ADAPT:

- Use dark contrast only for selected proof moments
- Translate expert detail into Japanese consumer questions

AVOID:

- Technology logos as the story
- All-dark uninterrupted pages
- Invented UI, connector relationships or technical labels
