# 商业画面制作

用户提供实图参考、要求商业渲染/功能效果，或反馈“不是同一种图片”时读取。本契约补充现有 Handoff，不新增入口，不批准产品、结构、Claim 或发布。

## 先选画面类型，再选模板

参考证据分 `PIXELS_VIEWED`（实际看图）、`DOM_ONLY`（只读页面结构）、`UNAVAILABLE`。只有实际看图可支持镜头、光影、材质、配色与构图结论；DOM 可支持轮播组织，不能支持“已对标视觉”。保留不可读链接，不根据 ASIN 猜画面。

| visual_type | 消费者要看见什么 | 合适制作方式 |
|---|---|---|
| `official_packshot` | 实际在售产品/组合 | 官方白底整套素材；单独核对渠道规则 |
| `commercial_scene` | 产品在什么场合完成什么动作 | 镜头匹配的官方产品素材与场景，具有真实接触、光影和遮挡 |
| `mechanism_visual` | 部件如何作用、过程与结果 | 官方局部/已批准 CG 与贴合作用位置的效果；有结构证据才做剖透 |
| `information_graphic` | 尺寸、配置、比较或边界 | 文字、图标和原生图表；有意选择的信息图 |

为当前新增或重开的资产记录：参考原图位置、实际看见的 2–3 个特点、借鉴原则、不迁移的内容。参考不贡献产品事实、参数或完整设计。统一品牌字体、颜色和语气，不要求整套使用同一机位和信息容器。

## Brief 要决定镜头与动作

先写 `对象 → 动作 → 可见结果`，再安排主体、镜头、场景和文字。每张至少决定：

- 类型、已看过的参考及单一视觉证据；
- 官方素材的机位、光向、可裁切范围和不可变特征；
- 场景的匹配透视、尺度、地面接触、前景遮挡；
- 特效的起点、作用面、终点、遮挡顺序与强度；
- 标题位置和负空间；桌面/移动各自的镜头与阅读路径；
- 实际工具/Renderer、所需输入与能力缺口。

白色顶栏、50/50 分栏、三卡片与胶囊标签是可选排法，不是全套默认骨架。“后期排字”不等于先把图片塞进固定文字模板。只有一个官方机位时围绕该机位设计场景；不能借“可变镜头”让 AI 发明产品另一面。

## 保真不等于抠图贴背景

保持官方 Product Layer 规则。分层是编辑和来源规则，不要求成片看起来分离。源图哈希一致不说明最终透视、接触和光线正确。

- 场景匹配产品透视、地平面、光向与色温；优先官方使用场景或匹配的棚拍/CG 素材。
- 接触阴影、投影、反射和遮挡依具体机位制作，不用一个通用椭圆阴影处理所有产品。
- 水、气、热、灰尘等独立效果贴合作用面；不能盖住核心部件，也不能像贴纸飘在外壳旁。箭头负责引导，不能代替动作本身。
- 精确日文、标签和参数最后独立排版。

机理画面按证据分级：有批准 CAD/结构渲染才做剖透/爆炸；只有官方外观与局部时做局部动作特写和外部过程示意；缺关键资料时明确缺哪张角度、结构或动作图，只阻塞受影响的镜头。功能示意标注不授权虚构管路、温度、行程或几何。不要用大水花和网格假装结构已解释。

## 代表图检查后再扩大制作

优先先做一张场景动作图和一张机理图；本轮只有一种类型时一张即可。保持未修改、已批准的精确资产。实际并排打开参考与成片，记录具体观察：

1. 输出仍是所选类型，还是退成文字说明海报？
2. 透视、光线、地面接触与遮挡是否一致？
3. 去掉标题后，能否看见对象、动作和结果？效果是否发生在作用位置？
4. 是否借鉴了参考的有效镜头和层级，同时保留自己的产品与设计？
5. 手机尺寸下关键动作及文字是否可读？

类型错误先改制作方法与镜头，不先改边框、颜色和标签数量。不要批量扩展同一种失败画面，再用数量证明完成。

用户已经确定方向或授权自行推进时，在现有授权内完成内部检查与修订，不重复问“是否继续”。模型观察如实标记，不冒充用户选案或现有 Whole-set/发布批准。用户否定画面类型时，保留原记录，重开受影响候选的视觉制作，不继承旧文件批准。

## A+ 展开理解，不只换尺寸

保留用户故事顺序。Gallery 用一个场景建立购买理由；A+ 同主题按生活价值、动作过程、局部机制/使用边界展开，每页有新增理解。产品素材可以复用，镜头与解释不能只是同一张图换成横版。移动版保留动作发生的位置，重新安排主次，避免把所有模块变成同一纵向卡片。

## 能力与完成状态如实记录

固定模板能验证信息结构；缺少场景、部件、效果和合成能力时，不能自称摄影/机理 CG 生成器。目标类型、实际 Renderer/工具、输入输出、替代方法与能力缺口写入 Run Manifest。若无法按目标制作，报告 `VISUAL_CAPABILITY_MISMATCH` 并定位缺口，不悄悄改成信息图交付。

在现有 PDP Spec 中，将类型写入 `product_images[].visual_type`、`aplus_modules[].visual_type`；轮播中类型不同的单元写入 `aplus_modules[].units[].visual_type`。当前 `render_v4` 没有完整商业成片输入通道，显式 `commercial_scene` / `mechanism_visual` 会停止模板渲染；应按本 Brief 使用具备相应能力的制作工具完成候选，不能删除类型字段来绕过。旧 Spec 未声明类型时保持兼容，但不受该代码保护覆盖，仍需实际看图检查。

旧 `VISUAL_QUALITY` 只调整模板参数和统计结构节奏。模板数量、源图哈希、PNG 解码、无溢出与结构分均不证明商业视觉达标。自写脚本也须做类型比对；未执行正式 Runtime，不声称正式 Flow 已跑通。

用 [visual-contract-example.json](visual-contract-example.json) 记录当前新增/重开资产和代表图观察，再执行：

```bash
python3 scripts/aplus_delivery.py visual-check \
  --contract /absolute/task/visual-contract.json \
  --output-dir /absolute/task
```

检查器仅读取类型冲突、参考等级、结构证据和绑定成片的哈希；不看图、不打审美分、不授予扩大生产或发布权限。`EVIDENCE_RECORDED` 仅代表记录完整，实际画面仍须由能看图的执行者比较。示例不是产品资产或已通过的观察记录。
