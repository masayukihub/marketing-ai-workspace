# 历史邮件证据、版式与渲染

适用于 `HTML_VISUAL`、重新设计和用户要求“参考过去推送”的任务。目标是让真实历史邮件中的有效视觉特征进入可编辑 HTML，并能解释继承依据。局部文案修改不必重跑完整流程。

## 1. 找到真正相关的邮件

优先使用已连接 Gmail 工具，读取用户指定的活动、阶段和品牌。先围绕活动名称、年份、Amazon / Prime Day / セール 等词检索，再根据真实返回的发件域、时间和主题缩小范围。营销邮件可能在收件箱的测试地址或转发中，不能只搜 `in:sent` 就断定没有历史。

任务中已有可核对的邮件原文、HTML 或图片时直接复用，不重复要求用户提供。保留工具返回的来源标识和读取时间；工具连接成功、搜索命中或只见主题不等于已读取正文。

`assets/history-recipes.json` 的 `reference_lookup` 提供脱敏的历史活动检索词、日期与需查看区域，用于定位具体参考，不是已读取凭据。匹配到真实邮件后，在私有索引中把它关联至稳定 reference ID；不要仅凭相似主题冒用该 ID。新邮件适合当前任务时可提炼新候选，现有四类不是所有邮件的完整目录。

分类为实际推送、测试、重复、转发与非 EDM 沟通。去重优先看稳定邮件标识、主题/日期和内容；测试版本可帮助辨认制作过程，但不能单凭测试主题宣称实际发送。根据当前任务选择少量最相关样本，说明每封贡献什么：活动开售结构、品类主题、商品卡、截止提醒等。不能只因“同是促销”就把 Last Call 的紧迫语气套到首发邮件。

## 2. 证据能支持什么

| 实际取得的证据 | 可以支持 | 不能自动支持 |
|---|---|---|
| Metadata / 搜索摘要 | 来源定位、主题、日期 | 完整文案、版式、实际推送效果 |
| 纯文本正文 | 内容顺序、Subject/Preheader、CTA 文案 | 色彩、产品图组合、间距、移动重排 |
| HTML 原文 | 可解析结构、样式声明、图片和链接位置 | 图片实际加载、完整视觉表现、客户端兼容 |
| 已查看的 Hero 或部分图片 | 对应区域的构图、配色、字体层级 | 整封模块顺序、整封移动表现 |
| 完整邮件截图，或加载完整的 HTML 渲染 | 对应宽度下的可见布局、视觉节奏 | 其他宽度、其他客户端、销售效果 |

逐封记录取得的层级、完整性、实际查看范围和资源缺口。视觉结论应来自实际查看的图片或渲染，不能把模型从主题联想到的“秋色”当作原邮件特征。历史图片自身包含完整邮件时也要检查是否截断、缩略、含编辑器外框或缺失页尾。

Gmail 原文、收件人、地址、个人退订 token、跟踪参数和证据截图保存在任务的受限工作区。代码仓库只保存脱敏结构、脚本和合成测试；不要把整封私人邮件复制成公开 fixture。公共 Recipe 不等于当前用户邮箱里那封邮件已经读取。

## 3. 把参考转换为可执行版式

读取 `assets/history-recipes.json`，选取适合本次任务的结构候选，并用实际证据核对。至少说明：

- Hero：活动标识、视觉主体、产品群和留白位置，标题与日期的层级。
- 商品区：主推/次级比例，左图右文或上下排，利益、优惠、价格与 CTA 的顺序。
- 整体节奏：场景图、色块、商品区、收束段之间的关系，以及哪些模块可省略。
- 移动处理：哪些列应堆叠，哪些图保持整体，文字和 CTA 是否仍易读。

需要新 Recipe 时先作为候选；不要修改旧冻结模板或自签正式批准。没有足够的视觉证据也可提出完整候选，但应写“基于已读内容的新设计”，不写“已还原/继承历史视觉”。部分证据只能支持部分继承。

历史不一定正确。剔除占位 Preheader（例如「ここにプレヘッダーを入れます」）、与主题无关的长商品表、重复说明、过期 No.1、旧券、旧日期和失效链接。保留有效的产品识别、促销层级与购买入口；历史 14 个商品不意味着新邮件也应放 14 个。

给出可审核的模块映射：

| 历史区域/证据 | 新稿区域 | 处理 | 可见变化与理由 |
|---|---|---|---|
| 实际参考区域 | 对应模块 | 继承 / 调整 / 新增 / 省略 | 构图、图文关系、背景、CTA 或内容长度 |

修改已有稿时再列“旧稿模块 → 新稿模块”。不要填没有证据的“继承 70%”，也不要把模板 ID、颜色或 HTML `data-*` 标签当作继承验收。

## 4. 主题与当前内容绑定

先写清唯一任务：用户为什么现在打开、看完后去哪里、主推商品承担什么角色。重新设计时给少量可区分的主题方向，推荐一个。Subject、Preheader 与 Hero 各司其职：

| 位置 | 职责 |
|---|---|
| Subject | 收件箱里的打开理由 |
| Preheader | 补足活动范围、品类或条件，避免复述标题 |
| Hero | 邮件内的主利益与视觉主题，连接产品和购买动作 |

用户已确认的标题保持不变。产品顺序服从当前商业角色和用户要求，不能由旧邮件的商品表决定。当前官方产品图、SKU、文案和 CTA 按模块绑定，历史商品图仅作参考；不得挪用旧图表达新型号、配件或安装关系。

未确认现价、折扣或 URL 不必停止整体设计。制作完整内部稿，省略未确认数字，以可编辑字段保存缺口；未知购买链接保持待配置、禁用真实跳转或使用明确的预览行为。不得默默替换成品牌首页并称为活动链接。缺官方产品图时保留标明缺图的版位，不能用 AI 仿制产品填满它。

如果使用 image_gen，只生成获准的背景、环境或道具。产品、Logo、UI 和精确文案保留独立层，采用当前官方/批准素材及可编辑排版；最终邮件长图从实际 HTML 导出。

## 5. 生成并检查实际输出

在 `skills/switchbot-japan-edm` 目录执行，任务输入和产物放在 repo 之外：

HTML 和历史计划只需 Python 3。离线长图需要 `scripts/requirements-offline.txt` 中的依赖；首次使用可执行 `python -m pip install -r scripts/requirements-offline.txt`。可选 `font_file` 指向已许可的日文字体，用于预览子集嵌入；原生发送 HTML 不嵌入字体。没有离线依赖时仍输出 HTML，并明确记录长图未生成。

```bash
python scripts/edm_history.py plan --brief <brief.json> --evidence <evidence.json> --out <plan-directory>
python scripts/render_edm.py --input <render-input.json> --plan <plan.json> --out <output-directory>
```

输入合同见 [portable-input-contract.md](portable-input-contract.md)。完整 HTML 与 PNG 的关系、依赖缺口和 QA 结果保存在 `qa-report.json` 与 `offline-render.json`；不能只凭 CLI 退出成功就称所有检查通过。

使用计划命令实际返回的路径，不猜测文件已生成。运行前检查脚本依赖、输入合同、Recipe 和素材路径；运行后读取结果与失败信息。这些命令说明接口，不能作为已执行、已测试或浏览器 QA 通过的证据。

生成的布局必须消费所选 Recipe 和当前商品列表。检查商品没有重复替代、主推权重明显、图片比例正确、CTA 对应实际下一步，且与模块映射一致。若 Recipe 更换后只有名称或颜色变化，结构继承尚未完成。

从实际 HTML 导出桌面及手机长图，记录 HTML hash、素材来源、渲染方式和实际宽度。优先在可用且获准的浏览器中检查所需宽度；浏览器被环境阻塞时，不绕过限制，也不把静态排版图冒充浏览器截图。离线排版可帮助审阅，但应明确标为“离线排版参考”；响应式、链接交互与邮件客户端检查继续显示未执行。

分别报告：HTML 生成、静态检查、离线排版、浏览器检查、邮件客户端、发送配置。任何一项没有实际执行都不能记为 PASS。旧 Ruby Runtime 未覆盖当前促销时保留 `BLOCKED_RUNTIME_SCOPE`，即使新增 adapter 成功输出内部候选，也不能改写原 Runtime 结论。

## 6. 交付与状态

视觉任务交付实际取得的内容：选源和证据限制、主题方案、历史/旧稿到新稿的模块对照、可编辑 HTML、实际 HTML 导出的长图、素材来源与 QA。缺少某项时明确缺口，不能在最终回答里链接不存在的文件。

短说明应回答：参考哪封、继承什么、主动改掉什么、当前还有哪些发送前事项。价格/日期/链接/素材或人工批准未确认时，完整视觉仍是内部候选。现有 Product Truth、项目 Visual Freeze、Final Human 与 ESP 规则继续生效；历史推送、脚本 PASS 和模型自评都不能代替当前人工批准，也不授权发送。
